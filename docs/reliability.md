# 可靠性加固

2026-10-17 逐项定下要引入的技术栈。原则：为了可靠性，该用的成熟组件就用，不因为项目小而省；优先用现成、近一年仍在维护、星数高、许可证和 AGPL-3.0 兼容的库。下表的星数和许可证是当天在 GitHub 上核对的；具体版本和用法在实施时按官方文档再核对。

## 1. 已定结论

| 层 | 结论 |
| --- | --- |
| 数据 | 不动：默认 SQLite，生产每天 04:05 一致性快照加主密钥备份到 R2。不引入 Litestream、CloudNativePG |
| 监控 | 做在后台里，不接外部监控系统。新增“监控”页：进行中和历史告警、各渠道健康（查账、预下单、查单、回调、熔断）、趋势图（下单和支付笔数、成功率、通知送达）。图表只在后台加载，不进收银台。起初用 ECharts（`apache/echarts`，Apache-2.0），2026-10-18 换成组件库 `@yreidev/ui` 的图表组件（基于 recharts，MIT），和概览页共用 |
| 告警 | Tillbox 自己用 Telegram 机器人单聊发给管理员，库用 `go-telegram/bot`（★1.9k，MIT；星数更高的 `go-telegram-bot-api` 2021 年后没有发布，不用）。在“设置 → 管理员通知”填机器人 Token（主密钥加密），点“添加接收人”得到 `https://t.me/<机器人>?start=<验证码>`，管理员在 Telegram 点 Start 后自动记下会话；可以绑定多人、解绑、发测试消息。Tillbox 用 `getUpdates` 长轮询收消息，不用配回调地址。告警开始和恢复各发一次，持续未恢复的按间隔再提醒。同一个机器人还发收款到账和付款申诉，见[第 6 节](#6-管理员通知) |
| 宿主机巡检 | 保留，继续发 Telegram。它覆盖 Tillbox 自己发现不了的：进程挂了、备份、磁盘、HTTPS 入口；后台配好 Telegram 后不再重复发业务告警，改为看 Tillbox 告警任务是否在运行、发得出去 |
| 容错 | 调外部接口（第三方易支付、支付宝、Telegram）用 `cenkalti/backoff`（★4.1k，MIT）统一重试退避，替换手写的退避；按渠道用 `sony/gobreaker`（★3.7k，MIT）熔断，熔断状态进监控和告警。商户通知的重发时间表按易支付官方对齐，不改 |
| 测试 | `microsoft/playwright`（★97.9k）写关键流程的浏览器端到端测试，桌面和手机宽度都跑，进 CI；`testcontainers-go`（★5k，MIT）在测试里起 PostgreSQL，替换脚本起容器；`uber-go/goleak`（★5.3k，MIT）检查后台任务的 goroutine 泄漏 |
| 供应链 | Renovate（★22.8k，以 GitHub App 安装）给 Go、pnpm、GitHub Actions、Dockerfile 开升级 PR；Trivy（★38.5k）扫发布镜像和前端依赖，有高危漏洞不发版；Syft（★9.7k）生成 SBOM，cosign（★6.4k）用 GitHub 身份免密钥签名镜像并附上 SBOM，上线前验签 |
| 部署 | 这次不引入 GitOps（Argo CD、Flux）：它会改变集群上所有服务的部署方式，还要先定仓库里的密钥怎么放，另起集群计划。Tillbox 继续用升级脚本，加上验签 |

不引入，及原因：

- Prometheus、VictoriaMetrics、Grafana、Loki、Alertmanager、Uptime Kuma、Gatus：监控按要求做在后台里，不接外部系统。
- QQ 官方机器人：先考虑过，后改用 Telegram。QQ 机器人只认 openid，要接收事件才能拿到；官方 Go SDK（botgo）2024-12 之后没有更新。
- River 任务队列：通知重试已经存库并有测试，换掉等于重写，而且只支持 PostgreSQL。
- go-playground/validator、testify：写法不同，对可靠性没有实际提升。
- Sentry：会把带支付信息的报错发给第三方，自建太重。
- failsafe-go：功能和 backoff + gobreaker 重叠，星数更少。

## 2. 告警规则

后台每 30 秒检查一遍（`internal/monitor/checks.go`），同一个问题按去重键算一条告警。

| 告警 | 级别 | 条件 |
| --- | --- | --- |
| 渠道现在不能收款 | 严重 | 启用的渠道配置不完整或不可用 |
| 查账连续失败 | 严重 | 启用的经营码渠道主窗口查账连续失败至少 3 次 |
| 历史补扫连续失败 | 提醒 | 启用的经营码渠道补扫连续失败至少 3 次 |
| 查账停摆 | 严重 | 启用的经营码渠道距上次成功查账超过 `max(5 分钟, 3 × 常规查账间隔)`；从没成功查过的，从这次启动后具备查账条件（已启用、配置齐全）起算。后台的查账状态按同一个阈值显示“查账停摆” |
| 第三方平台预下单连续失败 | 严重 | 第三方易支付渠道（含停用的，已下的单还要查）预下单连续失败至少 3 次；金额被第三方平台拒绝的不算 |
| 第三方平台查单连续失败 | 严重 | 第三方易支付渠道查单连续失败至少 3 次 |
| 不合格的第三方平台回调 | 提醒 | 24 小时内收到过验签或内容不合格的回调，之后没有合格的 |
| 没能通知到商户 | 严重 | 有放弃了的通知 |
| 流水异常待处理 | 提醒 | 有未处理的流水异常，详情按类型列出笔数 |
| 付款问题等人工 | 提醒 | 有等人工处理的申诉 |
| AI 自动处理出错 / 停滞 | 提醒 | 启用时上次运行出错；或超过 `max(10 分钟, 3 × 巡检间隔)` 没有运行 |
| 自动备份失败 | 提醒 | 数据库是 SQLite、开着自动备份，最近一次备份失败 |
| 自动备份停滞 | 提醒 | 数据库是 SQLite、开着自动备份，成功过，但超过 26 小时没有成功（关掉后再打开时，到期的话马上备份一份） |
| 归档任务出错 / 停滞 | 提醒 | 上次运行出错；或开着自动归档、成功过，但超过 48 小时没有成功 |

- 恢复：问题连续 2 分钟没再出现才算恢复，避免来回跳。
- 通知：告警开始、计数类告警的笔数变多、恢复时各发一次，一直没恢复的按设置的间隔再提醒（默认 1 小时，0 表示不提醒）；一轮里的变化合成一条消息。开始那条发出去了才发恢复。发送失败不记为已通知，下一轮重发。
- 发送失败的原因显示在监控页顶部、“设置 → 管理员通知”和每个接收人下面。宿主机巡检脚本在后台配好 Telegram 后不再重复检查业务问题，改为检查 Tillbox 的告警任务 5 分钟内有没有运行、最近一次发送有没有失败，见 [operations.md](operations.md#宿主机巡检)。
- 恢复的告警保留 180 天。
- 熔断打开的告警随第 2 步加入。

## 3. 数据

- 第三方易支付渠道的预下单、查单、回调状态存进设置表（`confirm_state:ch<编号>`），每轮确认任务后写回，重启不丢。预下单和查单的连续失败次数分开记，渠道卡片和监控页分别显示。删除渠道时一起删掉。
- 告警表 `alerts`：去重键、级别、标题、详情、处理页面、待处理笔数、开始、最近一次出现、恢复、最近一次通知成功的时刻。没恢复的告警按去重键唯一。
- Telegram：Token、提醒间隔、到账和申诉开关存设置 `telegram`（Token 用主密钥加密；旧设置里没有开关时按打开算），绑定的会话存 `telegram_chats`（会话 ID、名字、上次送达、上次失败）。监控任务的上次运行、上次发送和发送错误存设置 `monitor_state`，宿主机脚本读它。
- 迁移 `00005_monitor.sql`（SQLite 和 PostgreSQL 各一份）。
- 待发的业务消息存 `admin_events`（类型、订单或申诉编号、状态、排队和处理时刻，同一个对象只排一次），迁移 `00006_admin_events.sql`。

## 6. 管理员通知

2026-10-17 定：

- Telegram 的设置从监控页移到“设置 → 管理员通知”标签，监控页只显示状态和入口。机器人不只发告警，放在设置里更合适。左侧导航的“通知”是发给商户的异步通知，所以这个标签叫“管理员通知”。
- 除告警外再发两类业务消息：
  - 收款到账：订单变成已支付时发。只在到账时发，下单不发（下了单没付、最后过期的不打扰）。
  - 付款申诉：付款人在自助页一提交就发。系统自己开的申诉（流水异常、通知失败）不发；转人工后的提醒仍由“付款问题等人工”告警发。
- 内容：到账写实付金额（和订单金额不同时一并写出）、商户、渠道、商品名、订单号，测试单标出来；申诉写类型、申报金额、订单号。付款人账号、联系方式、申诉说明都不发：消息会存在 Telegram 的服务器上，和不接 Sentry 是同一个理由。消息末尾附后台对应页面的链接。
- 开关：到账、申诉各一个，默认打开。告警不能关：配好 Telegram 后宿主机巡检不再发业务告警，告警再能关就两边都不发了。
- 可靠性：把订单标成已支付（`order.markPaid`，所有到账都经过这里）和申诉入库时，在同一个事务里往 `admin_events` 排一条，提交后唤醒监控任务马上发。一轮里同一类合成一条消息，最多逐笔列 10 笔，其余只计数；发送失败的留着，下一轮（30 秒内）重发，失败记进 `monitor_state`，宿主机巡检能看到。没配好 Telegram、那一类关着、订单或申诉已经不在（或订单已不是已支付）的记为跳过，之后配好或打开也不补发。发完或跳过的保留 7 天。
- 排版（2026-10-17 补定）：用 Telegram 的 HTML 格式，“标题加引用块”：第一行表情符号加粗体标题，明细放进引用块，订单号用等宽字，最后一行斜体写站点名和时间；后台链接做成消息下方的按钮。动态内容（第三方平台原话、商户名、商品名）一律转义并截短，Telegram 解析不了的消息会整条拒收。按钮只用 https 地址，其他地址写进正文：Telegram 可能拒收本机或 http 地址的按钮（未确认），拒收会让整条消息发不出去。
- 测试消息可以选类型：告警开始、告警恢复、收款到账、付款申诉、全部发一遍。和真实消息用同一套排版，示例数据，标题标“【测试】”，不写库、不影响告警和队列。
- Token 输入框右侧加“粘贴”（`navigator.clipboard.readText()`，浏览器不让读时提示长按粘贴）和显示/隐藏按钮。原来在抽屉里，iPhone 上抽屉打开时 React Aria 会拦掉触摸滑动，可能导致长按粘贴菜单出不来；挪到设置页后是普通页面上的输入框。
