# 支付测试、监控与归档

## AI 自动处理与付款人申诉

后台“AI 与付款申诉”可以配置模型、启用自动查账（上游渠道的订单改为向上游查单）、补发通知及证据核验后的到账补认（只限经营码渠道）；付款人通过收银台链接或 `/help` 提交问题。配置、自动执行条件、查询凭证与数据范围见 [ai-support.md](ai-support.md)。AI 运行出错、停滞和等人工的申诉会在“监控”页告警。

## 后台支付测试

打开 `/admin/payment-test`，选择已启用商户、金额和 V1/MD5 或 V2/RSA，创建订单后打开收银台。测试单走所选商户的支付渠道，页面会显示该渠道能不能收款。经营码和上游渠道都需要真实付款（上游渠道按原价付款，在收银台选支付方式）；页面依次显示建单、确认付款和通知验签结果，每 3 秒刷新。未支付测试单可以关闭。

测试单共用所属渠道的正常金额池、查账或查单流程，`is_test=true`，不计入概览营业统计、商户易支付统计或订单列表 API。它只向本站固定测试接收端发送通知，不会给业务站充值；订单列表和 CSV 带测试标识。接收端只能确认已经由流水匹配或上游确认到账的测试单，不能标记订单已付。重复有效通知只增加接收次数。测试单并不能替代业务站实际充值验收。

检查渠道本身的连接用“支付渠道”页的“测试连接”：经营码渠道查一次账务明细，上游渠道调上游的商户信息接口，都不下单。模拟付款接口只在演示模式注册。

“支付渠道”页的“运行情况”一列显示每个渠道的状态：经营码渠道是查账进度和错误；上游渠道是预下单和查单各自连续失败的次数和原因、上次查单、上次回调和不合格的回调。上游渠道的这些状态存在数据库里，重启后保留。

## 监控和告警

后台“监控”页（`/admin/monitor`）列出现在有哪些问题。Tillbox 每 30 秒检查一遍，规则见 [reliability.md](reliability.md#2-告警规则)：渠道能不能收款、经营码查账、上游预下单和查单、上游回调、没能通知到商户的订单、待处理的流水异常、AI 自动处理、归档任务。同一个问题只算一条告警，问题消失 2 分钟后才算恢复，避免来回跳。页面上还有：

- 进行中的告警：严重的排在前面，写明开始时间、持续多久、有没有发出 Telegram，点“去处理”到对应页面。处理完点右上角“立即检查”，不用等下一轮。
- 渠道运行情况：每个渠道能不能收款，以及查账或上游的状态。
- Telegram 通知：机器人、接收人数、再提醒间隔、上次发出消息的时间；点“设置”到“设置 → 管理员通知”。
- 趋势：近 24 小时（按小时）、7 天或 30 天（按天）的新建和已支付订单、支付成功率、通知商户送达和失败的次数，不含测试订单，按北京时间分格。
- 最近恢复的告警：最近 30 条；恢复的告警保留 180 天。

侧栏“监控”右侧的数字是没恢复的告警数。

### Telegram 通知

Tillbox 用 Telegram 机器人单聊给绑定的人发三类消息，设置在后台“设置”→“管理员通知”（监控页上只显示状态）：

- 告警：开始、待处理笔数变多、恢复时各发一次；一直没恢复的，按设置的间隔再提醒（默认 1 小时，可设 0–24，0 表示不再提醒）。一轮里的几条变化合成一条消息。告警一直发，不能关。
- 收款到账：订单确认到账时发，写明实付金额（和订单金额不同时一并写出）、商户、渠道、商品名、订单号，测试单会标出来。不带付款人信息。默认发。
- 付款申诉：付款人在自助页提交申诉时发，写明申诉类型、申报金额和关联的订单号。付款人留的联系方式和说明不发，到“AI 与付款申诉”页看；转人工后的提醒由告警发。默认发。

消息的样子：第一行是图标加粗体标题（例如“🟢 收款到账 · ¥12.00”），明细放在引用块里，订单号用等宽字（手机上点一下就复制），最后一行是站点名和时间（北京时间）。消息下方有一个按钮，直接打开后台对应的页面（订单、申诉、监控页或告警的“去处理”）。按钮要用 `TILLBOX_PUBLIC_URL` 拼地址：没配时不带链接；配的是 http 地址时链接写在正文里，不做成按钮（Telegram 可能拒收这种按钮，整条消息会发不出去）。

到账和申诉消息在订单标成已支付、申诉入库的同一个事务里排队，提交后马上发，同一轮的几笔合成一条。发送失败的下一轮（30 秒内）重发，失败原因显示在“管理员通知”页、监控页顶部和接收人列表里。没配好 Telegram 时、或那一类消息关着时发生的到账和申诉直接跳过，之后配好或打开也不补发。

设置步骤：

1. 在 Telegram 里搜索 `@BotFather`，发送 `/newbot`，按提示给机器人起名字和用户名，复制它回复的 Token。也可以用已有的机器人，但它不能设了 Webhook，也不能有别的程序在用 `getUpdates` 收它的消息，否则绑定收不到。
2. 后台“设置”→“管理员通知”→“Telegram 机器人”，把 Token 粘贴进输入框（手机上长按粘贴不方便时，点输入框右侧的“粘贴”；右侧的眼睛图标可以显示出来核对），点“保存”。保存时会向 Telegram 核对 Token，通过后显示机器人的用户名。Token 用主密钥加密后存库。
3. “接收人”里点“添加接收人”，用要接收通知的 Telegram 账号打开弹窗里的链接（手机可以扫二维码），在机器人对话里点“开始”（Start）。机器人回复“绑定成功”，弹窗自动关闭，接收人列表里出现这个账号。链接 10 分钟内有效，只认单聊。
4. 点“发测试消息”，在菜单里选一种：告警开始、告警恢复、收款到账、付款申诉，或者“全部发一遍”（四种各发一条）。测试消息和真实消息排版一样，用示例数据，标题前标“【测试】”；不记告警、不进发送队列。确认手机上收到、样子正常。
5. 需要的话在“发哪些消息”里关掉收款到账或付款申诉、改告警的再提醒间隔，点“保存”。

要通知多个人就重复第 3 步。不想再收的，在接收人列表里点“解除”。在“机器人”一行填新的 Token 点“换机器人”会清空接收人，要重新绑定；“清除 Telegram 设置”删除 Token 和全部接收人，之后告警只显示在后台。

Tillbox 只在绑定期间（最多 10 分钟）向 Telegram 拉取消息，平时只发消息，不需要对外开放回调地址；服务器要能访问 `api.telegram.org`。

## 宿主机巡检

`scripts/tillbox-monitor.py` 适用于 Kubernetes（例如 k3s）上用 SQLite 的部署：在宿主机上由 systemd 定时器每 5 分钟执行一次，用 kubectl 进容器只读查询数据库，再用 Telegram 发提醒。新异常提醒一次，持续异常每小时提醒，恢复提醒一次，发送失败不推进去重状态。它覆盖 Tillbox 自己发现不了的问题：进程挂了、备份、磁盘、公网入口。

后台还没配好 Telegram 通知（没填 Token 或没有接收人）时，脚本也检查业务状态；配好以后，业务问题由 Tillbox 自己发，脚本改为只确认 Tillbox 的告警任务在运行、发得出去，不重复提醒：

| 检查 | 条件 | 后台配好 Telegram 后 |
| --- | --- | --- |
| 主窗口 / 补扫 | 任一启用的经营码渠道连续失败至少 3 次 | 不查，由 Tillbox 告警 |
| 查账停摆 | 任一启用的经营码渠道距最后成功超过 `max(5 分钟, 3 × 常规查账间隔)`，或具备查账条件后一直没成功过 | 不查，由 Tillbox 告警 |
| 通知 | 存在死信 | 不查，由 Tillbox 告警 |
| 归档 | 执行失败，或启用后 48 小时无成功执行 | 不查，由 Tillbox 告警 |
| Tillbox 告警任务 | — | 超过 5 分钟没有运行，或最近一次发送失败 |
| 备份 | CronJob 暂停、26 小时无成功执行，或最近失败尚未恢复 | 照常 |
| 磁盘 | 数据所在文件系统可用不足 1 GiB 或 10% | 照常 |
| 实例与入口 | 无可用实例，或 HTTPS `/readyz` 检查失败 | 照常 |

`/healthz` 是进程存活检查；`/readyz` 以两秒超时检查数据库。查账故障只告警，避免通过重启反复打断退避。脚本和 Tillbox 可以用同一个机器人：脚本只发消息，不收消息，不影响后台绑定。

### 安装

1. 把 `scripts/tillbox-monitor.py` 复制到 `/usr/local/lib/tillbox-monitor/`，把 `scripts/tillbox-monitor.service` 和 `tillbox-monitor.timer` 复制到 `/etc/systemd/system/`。
2. 新建 `/etc/tillbox-monitor.env`，权限设成 600，按下表填写。值里有空格时用单引号括起来，systemd 和 shell 都能读。
3. 运行 `systemctl daemon-reload` 和 `systemctl enable --now tillbox-monitor.timer`。

| 变量 | 说明 | 默认值 |
| --- | --- | --- |
| `TILLBOX_MONITOR_URL` | 公网就绪检查地址，例如 `https://pay.example.com/readyz` | 必填 |
| `TILLBOX_MONITOR_KUBECTL` | kubectl 命令 | `'k3s kubectl'` |
| `TILLBOX_MONITOR_NAMESPACE` | 命名空间 | `tillbox` |
| `TILLBOX_MONITOR_DEPLOYMENT` | Deployment 名称 | `tillbox` |
| `TILLBOX_MONITOR_DB` | 容器里的 SQLite 路径 | `/data/tillbox.db` |
| `TILLBOX_MONITOR_BACKUP_CRONJOB` | 备份 CronJob 名称；设成空值就不检查备份 | `tillbox-backup` |
| `TILLBOX_MONITOR_TELEGRAM_SECRET` | 存提醒目标的 Secret，写成 `命名空间/名称`；Secret 里的键是 `telegram-token` 和 `telegram-chat-ids`（JSON 数组） | 无 |
| `TILLBOX_MONITOR_TELEGRAM_TOKEN`、`TILLBOX_MONITOR_TELEGRAM_CHAT_IDS` | 不用 Secret 时直接写机器人令牌和会话 ID（多个用逗号分隔） | 无 |

脚本放在别的路径时，不要改仓库里的 service 文件：用 `systemctl edit tillbox-monitor.service` 写一个覆盖文件，先写一行空的 `ExecStart=` 清掉原值，再写新的 `ExecStart=`。

手动检查：

```sh
set -a; . /etc/tillbox-monitor.env; set +a
python3 /usr/local/lib/tillbox-monitor/tillbox-monitor.py --dry-run
systemctl list-timers tillbox-monitor.timer
journalctl -u tillbox-monitor.service
```

dry run 只读、不发送通知、不更新去重状态。机器整体断电仍需机器外监控。

## 首页和后台安全入口

“设置 → 站点”管三件事：站点名称、直接打开域名时看到什么、后台要不要先打开入口链接。

站点名称显示在后台左上角、登录页、浏览器标签、收银台标题上，也是手机“添加到主屏幕”时的应用名。

首页（`/`）可以选四种：

- 付款人自助页：默认，和以前一样进入 `/help`。
- 自定义页面：贴一整段 HTML，最多 512 KB，原样返回。响应带 `Content-Security-Policy: sandbox …`，页面里的脚本在隔离的来源里运行，读不到本站的 cookie 和本地存储，也不能带着登录状态调后台接口。图片、样式写在页面里或用外部地址。保存前可以点“预览”。
- 跳转到其他网址：用 302 跳到填的 http 或 https 地址，浏览器不会记住，改回别的首页立即生效。
- 404：和不存在的路径一样。

这里只改 `/`。收银台（`/cashier/…`）、付款人自助页（`/help`）和易支付接口照常工作，收银台里进自助页的链接直接指向 `/help`。既不是前端页面也不是文件的路径一律返回 404。

后台安全入口默认关闭。开启后：

- 没打开过入口链接的浏览器访问后台（`/admin…`）、登录页（`/login`）和后台接口（`/web-api/admin/…`、`/web-api/auth/…`），得到的和不存在的路径一样是 404。
- 入口链接是 `https://<域名>/admin?entry=<密钥>`。打开后浏览器记一个 cookie（HttpOnly，400 天），再跳到去掉密钥的地址；cookie 里存的是密钥的摘要。放行后照常输密码登录。
- 开启和“换一个链接”时，当前浏览器自动放行。换链接后，旧链接和其他已放行的浏览器全部失效。
- 入口链接存进密码管理器。忘了可以在服务器上查看、更换或关闭：

```sh
docker compose exec tillbox tillbox entry          # 显示入口链接
docker compose exec tillbox tillbox entry reset    # 换一个链接（没开时开启）
docker compose exec tillbox tillbox entry off      # 关闭
```

命令直接改数据库，运行中的服务马上生效，不用重启，审计日志里操作人记为“命令行”。链接里的域名取 `TILLBOX_PUBLIC_URL`，没配时显示占位，自己换成实际域名。二进制部署用相同的数据目录、数据库和主密钥环境变量运行 `./bin/tillbox entry`。

Telegram 消息下方的按钮在 Telegram 自带的浏览器里打开时，那个浏览器也要打开过入口链接，否则看到 404：在里面打开一次入口链接，或者让 Telegram 用系统浏览器打开链接。

## 记录保留和恢复

后台 `/admin/operations` 默认每日自动检查一次：流水原始响应和通知尝试在线保留 90 天，审计日志 365 天，可修改或暂停。每次最多处理 15,000 条，后续运行继续。所有订单、金额、流水编号、指纹、关联、通知最终状态及最后一次通知尝试长期保留。未完成通知、争议订单及存在未解决异常的流水证据不清理。

过期记录先压缩为 JSONL.GZ，再用配套主密钥加密存入 `/data/archives/*.jsonl.gz.enc`，文件权限 600、目录 700；文件与目录同步落盘后，才在同一数据库事务内登记 SHA256 清单并清理在线副本。文件写入或事务失败时保留在线记录；事务回滚可能留下没有清单的加密副本，保留待核查即可。归档文件不自动删除，磁盘巡检负责容量提醒。

备份要包含数据库、`master.key` 和整个 `archives/`。恢复时三者配套恢复，先校验备份包内 SHA256，再检查数据库。不要只恢复数据库或只保留最新数据库而删除归档目录。

后台可按批次下载：服务先检查密文 SHA256，解密后返回 `.jsonl.gz`。每行含 `version:1`、`table`、`id`、`data`；表名为 `transactions.raw`、`notify_attempts` 或 `audit_logs`。可以解压检索历史证据。需要重新导回在线库时，先停止服务并备份：`transactions.raw` 按 ID 恢复 `raw`，另两表按原 ID 导入完整 `data`（已有同 ID 记录不得覆盖）；在事务内核对条数，恢复后保留原归档与清单。通知历史恢复不改变订单或通知队列状态，不会触发重新充值。

## 版本与升级

`VERSION` 定义版本，`tillbox version` 同时显示提交 SHA；镜像 OCI 标签包含版本与提交。`make image IMAGE=tillbox:0.1.0` 仅构建 linux/amd64。发版用 `make release VERSION=x.y.z`；CI 和本机 `make ci` 的检查内容、版本标签触发的镜像归档（不自动公开发布）和完整步骤见 [release.md](release.md)。

升级前执行一次备份并确认上传校验成功；再部署新镜像；Kubernetes 下更新 Deployment，保持单实例 Recreate。启动时自动执行 goose 增量迁移。已发布的 `00001_init.sql` 冻结，后续变更新增迁移；本次 `00002_operations.sql` 为现有订单补 `is_test=false` 并增加接收与归档表。

宿主机巡检脚本要读新版本建的表时（例如 `00005_monitor.sql` 加的 `telegram_chats`），先升级镜像、等新实例启动完成迁移，再把新脚本换到宿主机；旧脚本读新库没问题，新脚本读旧库会报“数据库巡检失败”。升级前快照可在停机后恢复配套旧镜像；回滚前先处理升级后新增订单与通知，不能让两套实例同时查同一支付宝账户。
