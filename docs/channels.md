# 支付渠道

经营码和上游易支付都是“支付渠道”：在后台用列表管理，两种都可以配多个，每个商户选用其中一个。本文是这次重构的方案和已定结论（2026-10-17 定稿），实现进度见文末。

## 1. 已定结论

| 项 | 结论 |
| --- | --- |
| 范围 | 只重构渠道层。易支付协议层、订单、通知、后台登录、AI 申诉门控保留，改为按渠道工作 |
| 渠道类型 | 支付宝经营码（推断型：查账加金额尾数）、上游易支付（确认型：预下单、回调、查单）；本地开发另有演示渠道 |
| 分流 | 每个商户指定一个渠道；改渠道只影响之后的新订单 |
| 数量 | 两种渠道都可以配多个，每个渠道单独启用、停用 |
| 上游协议 | V1（MD5）和 V2（RSA）都支持，每个上游渠道自选 |
| 支付方式 | 上游渠道勾选开放的 `type`（alipay、wxpay、qqpay 等）；经营码渠道只有 alipay |
| 付款页 | 以 Tillbox 收银台为主：上游给二维码时在收银台展示；只给跳转链接时，收银台给“去付款”按钮 |
| 过期后才确认 | 上游确认的付款自动到账并通知商户；订单过期后才确认的，另记一条待处理异常，提醒到商户后台核对是否入账 |
| 退款 | 和现在一样不支持接口退款 |

## 2. 数据

- 新表 `channels`：编号、类型、名称、启用、配置（JSON，密钥字段用主密钥加密）、备注、创建和修改时间。
- 订单和流水原有的 `channel` 列改存渠道实例键 `ch<编号>`。金额池、对账候选、查账活跃判断、流水去重都按这个键隔离，不同渠道的数据互不影响。
- `merchants` 增加 `channel_id`。
- 新表 `upstream_payments`，记录上游预下单的结果：订单、渠道、上游订单号、付款信息类型（二维码、跳转、唤起链接）和内容、上次查单时刻及错误。
- 升级迁移：已有的支付宝设置变成 1 号经营码渠道（加密后的私钥原样沿用）；历史订单、流水和查账进度都归到 1 号渠道。商户选第一个启用的渠道（线上就是 1 号渠道；本地演示库里经营码没启用时选演示渠道）。线上升级不需要手工操作。

## 3. 运行方式

### 3.1 渠道注册表

启动时从库里加载渠道，按类型构造实例；后台增删改渠道后立即生效，不用重启。下单、收银台、查账、回调都通过注册表找到订单所属的渠道实例。

### 3.2 经营码渠道

- 每个启用的经营码渠道各有一个查账任务，进度、退避、补扫队列各自独立。
- 一个支付宝账户只能配一个经营码渠道：两个渠道查同一个账户时，一笔付款可能让两边各到账一单。后台拒绝重复的应用 ID 和经营码。
- 金额尾数按渠道分配，同一金额在不同经营码渠道可以同时使用相同的应付金额。
- 迟付、错付、申诉补认等规则不变，只在本渠道的订单和流水之间推断。

### 3.3 上游易支付渠道

- 下单：调用方传了 `type` 时，当场向上游预下单。`out_trade_no` 用 Tillbox 平台订单号，`notify_url` 是 `/web-api/channels/<编号>/notify`，`return_url` 是 Tillbox 收银台。预下单失败时向调用方返回“支付通道暂时不可用”，订单保持待支付，调用方用同一订单号重试会再预下单一次。调用方没传 `type`、而渠道又开放了多种方式时，付款人在收银台选定后再预下单。
- 金额：按原价付款，不加尾数。
- 到账：
  - 收到上游回调后先验签：V1 用 MD5，V2 用 RSA，并检查时间戳不超过 300 秒；再核对商户号、平台订单号和金额，都对上才确认到账。
  - 定期查单兜底：待支付订单每 15 秒查一次，过期后 10 分钟内每分钟查一次。付款人点“我已付款”时立即查一次。
  - 上游订单号作为流水号入库（同一渠道内唯一），重复回调幂等。支付宝或微信的交易号记在流水的交易号字段，付款人申诉时可以填它。
  - 金额不符时不到账，记少付或多付异常；已支付的订单又收到另一个上游单号的确认，记重复付款异常。
- 上游地址要求 HTTPS（本机地址除外），请求不跟随重定向；查单和回调失败记在渠道状态里，运维巡检可见。

### 3.4 演示渠道

只在 `TILLBOX_DEMO=true` 时可以创建，流水存在内存里，用 `/web-api/dev/pay` 模拟付款。这种模式启动时如果还没有任何渠道，会自动建一个演示渠道。

## 4. 后台

- 新增“支付渠道”页：列表、按类型新建、编辑、测试连接、启用停用；只有没有订单、流水，也没有商户在用的渠道才能删除（不能删时按钮置灰并说明原因），其余只能停用。原“设置 → 支付宝收款”移到这里，作为经营码渠道的配置。
- 商户页：每个商户选择一个渠道；新建商户默认选第一个启用的渠道。
- 订单和流水页：显示渠道名称，可按渠道筛选。
- 支付测试：按所选商户的渠道下单。
- 运维巡检：按渠道显示查账或查单状态。

## 5. AI 与付款人自助

- 申诉补认（核对真实流水后补认迟付）只适用于经营码渠道。上游渠道订单的“未到账”申诉会触发一次查单，其余转人工。
- 没有订单号的申诉，在所有经营码渠道的流水里查找。

## 6. 不做

接口退款转发、上游关单、同一商户按支付方式拆分到不同渠道、渠道之间自动兜底切换。

## 7. 实施顺序

1. 渠道表和升级迁移、渠道注册表；经营码改成按实例工作，支持多个查账任务；现有测试全部改造通过。
2. 上游易支付渠道：V1、V2 客户端，预下单、回调、查单、确认到账。
3. 网关和收银台：按商户的渠道下单、选择支付方式、展示上游付款信息。
4. 后台：支付渠道页、商户选渠道、订单与流水显示、支付测试、运维巡检。
5. AI 与自助适配，文档；SQLite 和 PostgreSQL 全量测试；本地预览端到端验证（用 Tillbox 自己当上游）。

## 8. 进度

2026-10-17 第 1–5 步的本地实现完成，尚未提交和发布：

- 本地预览用 Tillbox 自己当上游做了端到端验证：测试连接、收银台选择支付方式、上游不支持的方式预下单失败、二维码付款、回调到账、商户收到通知、订单详情显示上游单号。
- 收银台在桌面和手机宽度下截图检查过；后台“支付渠道”页只做了类型检查和构建，没有在浏览器里逐项点过。
