# 易支付兼容取舍

目标：已经用易支付收款的站点只要把地址、商户 ID 和密钥换成本系统的就能直接用，不用改它们的代码；用官方 V1、V2 SDK 写的商户也能直接接入。

协议本身按官方服务端和官方 SDK 对齐，细节见 [epay-protocol.md](epay-protocol.md)。本文只写两件事：常见调用方实际怎么用，以及本系统在哪些地方有意和官方不同。

## 1. 常见调用方怎么用

常见的易支付调用方几乎都只用 V1（MD5），用法上有这些差别，本系统都要接得住：

- **下单**：`/submit.php` 有表单 POST，也有 GET 跳转（弹窗或链接）；`/mapi.php` 用 POST。
- **额外参数**：`device`（`pc`、`mobile`）、`cid`、`clientip` 等，都参与签名，所以要对收到的全部参数验签。
- **签名**：有的先在参数里放一个空的 `sign` 再签名；签名都只跳过空串。
- **`mapi.php` 的返回**：读 `code==1`、`payurl`、`qrcode`；有的手机端优先用 `payurl2`，没有时改用 `payurl`。
- **查单**：`/api.php?act=order`，有的把 `act=order` 和其他参数一起放在 POST 表单里（见第 2 节）。
- **退款**：`POST /api.php?act=refund`，有的先用 `out_trade_no` 试，再用 `trade_no` 试。
- **通知**：GET 和 POST 都有人收，回 `success`。
- **通知里的 `money`**：有的不检查；有的按数值和订单金额比较，误差超过 0.01 元就拒绝；有的按字符串严格比较，必须和下单时的 `"10.00"` 一模一样（见第 2 节）。
- **`type`**：一般是 `alipay`、`wxpay`，有的允许管理员自定义；有的收到回调后会用里面的 `type` 覆盖订单记录的支付方式。

## 2. 调用方和官方实现对不上的地方

下面两条都是调用方自己的问题，在这里只做记录，不需要本系统修复。

1. **表单里放 `act`**：有的调用方把 `act=order` 放在 POST 表单里，而官方只从查询串读 `act`，所以对官方服务端查单会得到 `{"code":-5,"msg":"No Act!"}`。
2. **按字符串比对金额**：官方通知会把 `10.00` 发成 `10`（见规格第 10.4 节），按字符串比较 `money` 的调用方对接官方服务端时，整数金额的订单全部会被判成"金额不符"。

## 3. 本系统和官方不同的地方

| 项 | 官方 | 本系统 | 原因 |
| --- | --- | --- | --- |
| 通知里的 `money` | 先转成浮点数再拼串（`10.00` → `10`） | **原样回传下单时收到的字符串** | 兼容按字符串严格比较的调用方。按数值比较的调用方不受影响 |
| `api.php` 从哪读参数 | `act` 和查单参数只从查询串读 | 查询串和表单都读，两边都有时以表单为准 | 兼容把 `act` 放在表单里的调用方 |
| 其他 `/api/*` 接口 | 只收 POST 表单 | 查询串和表单都读，规则同上 | 读参数统一用一套规则。两个跳转下单接口仍完全按官方规则读（见规格第 4 节） |
| `name`、`param` 等字段 | 入库前做 HTML 转义，通知里带回转义后的值 | 原样存，原样带回 | 转义是官方实现的副作用，不是协议要求 |
| 重复下单 | 只在 10 天内去重；原订单没付款就沿用原单号 | `pid + out_trade_no` 永久唯一；原订单已过期或已关闭时报错"该订单(…)已失效，请更换订单号重新发起支付"，其他规则和官方相同 | 避免查单时同一个订单号查出两笔；过期订单的应付金额可能已经分给别的订单，不能再拿来收款 |
| 不支持的 `type` | 跳转到收银台，让付款人换支付方式 | 直接报错，例如"暂不支持微信支付" | 一期只有支付宝；不能把其他方式悄悄当成支付宝 |
| 不传 `type`（只有跳转下单允许） | 进收银台让付款人选 | 按 `alipay` 处理，直接进收银台 | 只有一种支付方式可选 |
| 通知请求 | 不校验 TLS 证书 | 校验 TLS 证书 | 安全；调用方站点一般都有正规签发的证书 |
| 通知重试 | 立即发一次，之后在约 1、3、19、55 分钟各重试一次，然后停止 | 前 5 次和官方相同，之后在约 2、6、24 小时再各重试一次，然后进入死信，可以在后台手动重发 | 自建的调用方可能会短时间停机 |
| 退款 | 按通道退款 | 一期两个退款接口都返回 `code=-1`，提示"当前支付通道不支持API退款"；`refundquery` 返回"退款记录不存在" | 经营码收款没有退款接口，只能人工转账退回 |
| 代付和结算 | 有 | `/api/transfer/*` 返回 `code=-5` 和"接口方法不存在"；`act=settle` 返回空列表 | 本系统没有代付，也没有余额结算 |
| 商户余额字段 | 返回商户的余额 | `act=query` 和 `merchant/info` 里的 `money` 固定为 `"0.00"` | 钱收进支付渠道的账户，商户不单独结算，本系统不记余额 |

## 4. 下单的返回

无论哪种返回方式，给出的都是本系统收银台的绝对地址。**不要直接给经营码链接**，否则付款人看不到加了尾数之后该付多少钱。

- **V1 `mapi.php`**：同时返回 `payurl` 和 `qrcode`，都指向收银台。不返回 `payurl2`：调用方没拿到它时会改用 `payurl`，而收银台本身会适配手机。
- **V2 `create`**：
  - `method=jump`，或者 `device` 不是 `pc`：返回 `pay_type=jump`；
  - 其他情况：返回 `pay_type=qrcode`；
  - 两种情况下 `pay_info` 都是收银台地址；
  - `method` 为 `jsapi`、`scan`、`app`、`applet` 时，直接报错，提示不支持。
- **跳转下单**（`submit.php`、`/api/pay/submit`）：验签并建单后，用 303 跳转到收银台。

## 5. 金额尾数和通知里的 `money`

付款人实际要付的金额，是在订单金额上加了尾数的，例如 10.00 变成 10.03。但调用方只认自己下单时填的金额，所以：

- 通知和跳回 `return_url` 时，`money` 都原样回传下单时的字符串；
- 查单接口返回的 `money` 是订单金额，按两位小数格式化，不是实付金额；
- 实付金额由本系统另外保存，只在后台展示。

## 6. 订单状态怎么对外表示

本系统内部的订单状态比官方多，例如"已过期"和"已关闭"。对外只用官方的状态值：

- 未付款、已过期、已关闭的订单，`status` 都是 0；
- 已付款的订单，`status` 是 1；
- 2、3、4 这三个值一期用不到。

同一笔订单只会有一个最终结果。通知可能会重复送达，调用方自己会处理幂等。
