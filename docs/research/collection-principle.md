# 收款原理：经营码 + 账务明细查询 + 金额尾数匹配

不签约商户号、手机上也不挂监听软件，靠服务端定时查账单确认到账。本文是方案结论，数值是初始建议值，开发时可调。

## 1. 整体链路

```
调用方下单 10.00 → 分配应付金额 10.03（占住这个金额）→ 返回收银台
付款人在收银台看到 10.03 和经营码 → 支付宝扫码，手动输入 10.03 付款
服务端定时查支付宝账务明细 → 流水入库
  → 有一笔收入 10.03，时间在订单有效期内，且只对得上这一单 → 确认到账
  → 按易支付格式通知调用方，失败重试
```

- **收款码**：支付宝经营码，是静态码，内容是 `https://qr.alipay.com/...` 开头的链接。钱直接进收款人的支付宝账户，付款人要自己输入金额。
- **查账**：在同一个支付宝账户下建一个开放平台**网页应用**，调 V3 账务明细查询接口 `GET /v3/alipay/data/bill/accountlog/query`。
- **归属**：流水里没有我们的订单号，只能靠"应付金额唯一 + 时间窗口"推断是哪笔订单。**这是推断，不是逐单凭证**，同时同额、迟付、错付都可能对错单，必须有异常处理和人工关联。

## 2. 支付宝查账接口

| 项 | 内容 |
| --- | --- |
| 接口 | `GET /v3/alipay/data/bill/accountlog/query` |
| 查询参数 | `start_time`、`end_time`（格式 `YYYY-MM-DD HH:mm:ss`）、`page_no`、`page_size`（最大 2000） |
| 请求签名 | `Authorization: ALIPAY-SHA256withRSA app_id=…,nonce=…,timestamp=…,sign=…`；待签名串为 `认证串\n方法\n路径和查询串\n请求体\n` |
| 响应验签 | 用支付宝公钥验 `alipay-signature`，待验签串为 `alipay-timestamp\nalipay-nonce\n响应体\n`；**验签不过的响应一律丢弃** |
| 返回 | `page_no`、`page_size`、`total_size`、`detail_list` |
| 流水字段 | `account_log_id`（流水号）、`trans_dt`（时间）、`trans_amount`（金额）、`direction`（收支方向）、`alipay_order_no`、`merchant_order_no`、`trans_memo`、`other_account` |

当前验证范围：请求签名、响应验签和数据解析已用本地假服务器测试；生产已完成真实账务查询、一笔小额付款自动匹配和业务站充值，重复通知未重复增加余额（2026-10-16，见 integration.md）。

仍需实际账户确认：
- 网页应用是否默认就有账务明细查询权限。
- 一笔付款要过多久才能在这个接口里查到。
- 接口的限流阈值。

密钥：应用密钥对由本系统生成（RSA 2048 位及以上），私钥加密存库，公钥给用户上传到支付宝；用户再把支付宝公钥填回来。

## 3. 金额尾数池

- 应付金额 = 原价 + 偏移。偏移从 1 分开始往上加，上限可配（1–99 分），**只加不减**，所以付款人会多付几分到几毛。
- 从最小的可用金额开始挑。**同一个应付金额，同时只能有一个待支付订单**（跨所有商户共享，因为收的是同一个账户）。
- 订单结束后，这个金额要冷却一段时间才能再分配，默认 600 秒（可配 60–3600）。
  - 主动关闭的从关闭时刻算；自然过期的从原定到期时刻算，不因为过期处理晚了而重新计时。
  - 已付款的订单也要冷却，防止紧跟着的重复付款串到下一单。
- 金额全被占满时，下单失败并给出最早可重试时间。
- 订单有效期可配（60–1800 秒）。
- 容量估算：99 个金额、5 分钟有效期加 10 分钟冷却，同一个标价每分钟大约只能接 6.6 单。不同标价的候选金额会重叠（10.00 的 +5 分和 10.03 的 +2 分都是 10.05）。

## 4. 匹配规则

只看收入流水。候选订单条件：

1. 流水金额 = 订单应付金额；
2. 流水时间早于订单到期或主动关闭时刻；支付宝时间只精确到秒，下单边界按“流水时间 + 1 秒 > 创建时刻”判断，避免同一秒内付款漏匹配；
3. 流水时间早于这个金额被释放的时刻。

判定：

| 情况 | 结果 |
| --- | --- |
| 恰好一个候选，且这单还没付过 | 自动确认到账 |
| 多个候选 | 记为"匹配不唯一"，交人工 |
| 候选那单已经付过了 | 记为"重复付款" |
| 没有候选，但订单结束后 24 小时内到了同额付款 | 记为"结束后付款"，**不自动补认** |
| 没有候选，同一时段只有一个待付订单但金额对不上 | 记为"少付"或"多付"，关联到那一单 |
| 比该渠道首个订单还早的历史收入 | 保存流水，标为“不参与”，不产生异常 |
| 其余 | 记为"无法匹配的收入" |

人工操作：把一笔流水手动关联到一个订单（确认到账），或撤销已有关联（进入争议状态）。每次操作都要留操作人、时间和理由。

整批流水先入库再对账，按付款时间排序。中途出错留下的“待处理”收入在后续轮次继续处理，已分类的异常等待人工处理，不反复自动改判。

## 5. 查账节奏

| 项 | 建议值 | 说明 |
| --- | --- | --- |
| 常规间隔 | 60 秒 | 没有待付订单时 |
| 活跃间隔 | 8 秒 | 有未过期的待付订单时 |
| 最小间隔 | 8 秒 | 收银台"我已付款"可以让下一轮提前，但两轮之间不少于这个值 |
| 收尾期 | max(60 秒, 安全延迟 + 活跃间隔) | 订单结束后仍保持高频一小段时间 |
| 安全延迟 | 10 秒 | 每次查询的结束时间 = 现在 − 安全延迟 |
| 窗口重叠 | 5 分钟 | 和上一轮窗口重叠，靠流水号去重 |
| 补扫 | 每分钟回看 10 分钟；每小时回看 6 小时；每天回看 7 天 | 补迟到的流水 |

其他规则：
- 间隔从上一轮**结束**开始算；同一时间只有一轮查询在跑，多个"我已付款"请求合并成一轮。
- 主窗口最多查询最近 24 小时；停机缺口最多回看 30 天，较早的部分进入补扫队列。每分钟回看 10 分钟并入主窗口；每小时、每天的补扫独立排队，每轮主窗口后最多拉一个时间段，先做停机补拉，再做较短回看。
- 补扫进度、重试时间和三档补扫时刻持久化，重启继续。补扫失败独立退避，普通历史查询失败不阻止最近付款确认；限流和凭据错误让两条通道一起等待。每个时间段若过密仍可能触发多次切窗查询，因此“一段”不等于“一次 HTTP 请求”。
- 一页超过 2000 条时，把时间窗口对半切开再查。
- 失败按指数退避，并遵守接口返回的重试等待时间；凭据或权限错误至少停 15 分钟，避免反复打接口。
- 同一个流水号再次出现但内容变了，记为冲突，不自动覆盖。
- 单条流水解析不了（金额、时间格式不对或这一条的 JSON 读不了）时，原文照存并记“流水解析不了”的异常，不参与匹配，也不能关联订单；同一批的其他流水照常入账，查账不算失败。时间读不出来按入库时刻记。没有流水号的用原文摘要代替。之后支付宝返回同一流水号能解析的内容时，按新内容替换并重新对账，异常自动记为已处理。
- 所有间隔重启后从数据库恢复，改设置不需要重启。

## 6. 局限

- 只能收支付宝。微信个人收款有没有等价的账单查询接口，未确认。
- 付款人要手动输入金额，输错就进异常。
- 确认速度 = 安全延迟 + 查账间隔 + 支付宝账单出现在接口里的延迟。
- 不能原路退款，只能在后台标记"已在外部退款"。
