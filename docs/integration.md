# 商户接入与真实收款验收

## 1. 接入信息

先在“支付渠道”建好至少一个可收款的渠道（支付宝经营码见 [部署文档](deploy.md#6-支付渠道配置) 第 6 节，上游易支付见第 3 节），再在“商户 → 新建商户”创建一条记录，填写名称、选择支付渠道并启用；新商户默认选第一个启用的渠道。商户改渠道只影响之后的新订单。接入弹窗提供接口地址、商户号 `pid` 和 MD5 密钥 `key`；可从“查看密钥”重新打开。若限制通知和回跳域名，将调用方实际域名加入白名单。

调用方一般用 V1：在调用方后台把易支付地址填成 Tillbox 的根地址（以 `/` 结尾），再填商户 ID（`pid`）和 MD5 密钥（`key`），支付方式选商户渠道开放的方式（经营码渠道只有 `alipay`）。接口下单和跳转下单都指向这个地址，不用在末尾加 `/admin` 或 `/cashier`。调用方必须能从公网访问 Tillbox，Tillbox 也必须能访问调用方的通知地址。

V2 商户另在商户设置里填商户 RSA 公钥，在“设置 → 平台密钥”获取平台公钥交给调用方；对应商户私钥由调用方保管。“只收 RSA”会拒绝明文 key 查单和 MD5 下单，不适用于仅使用 V1 的调用方。

## 2. 付款和通知

经营码渠道靠金额尾数区分订单：例如商户下单 `money=10.00`，Tillbox 可能分配应付 `10.01`。付款人必须按收银台的应付金额付款，通知和回跳的 `money` 原样返回 `10.00`，查单接口返回订单原价。不要将经营码地址直接给调用方代替收银台地址。上游易支付渠道按原价付款，不加尾数。

调用方下单的 `type` 必须是商户渠道开放的支付方式，否则下单失败。经营码渠道只开放 `alipay`；上游渠道开放哪些由后台勾选。

系统发送 GET 通知。V1 订单用 MD5，V2 订单用平台 RSA 签名；接收方应按全部参数验签并对订单幂等处理，成功时响应体含 `success`。失败自动重试，进入死信后可在“通知记录”中手动重发。到期的通知按商户轮流发送，每轮每个商户最多发 2 条，某个商户的通知地址很慢或连不上时不会拖慢其他商户。回跳只用于展示，调用方应以验签后的通知或查单结果确认充值。

## 3. 上游易支付渠道

上游易支付渠道把订单转给另一家易支付收款，Tillbox 仍是调用方面对的网关和收银台。在“支付渠道 → 新建渠道 → 上游易支付”填写：

- 接口地址：上游易支付的根地址，必须是 `https://`（本机地址除外）；填成 `…/submit.php`、`…/mapi.php` 也会自动去掉。请求不跟随重定向。
- 接口版本：V1 填上游给的商户号和 MD5 密钥；V2 填商户号，先保存渠道，再点“生成密钥对”（或导入已有私钥），把显示的商户公钥填到上游后台，再把上游的平台公钥填回来。私钥和 MD5 密钥加密保存，编辑时留空表示不改；V1 换了接口地址要重新填密钥，因为查询时密钥会明文发给上游。
- 支付方式：只勾上游真正开通、要给调用方用的方式。商户下单的 `type` 不在其中时，下单直接失败并提示可用的方式。

保存后点“测试连接”：V1 调上游的商户信息查询，V2 调商户信息接口并验签，用来核对接口地址、商户号、密钥和平台公钥；它不下单，也不产生费用。通过后打开“启用”，再到商户页给商户选这个渠道。

预下单时 Tillbox 把自己的平台订单号作为 `out_trade_no`，回调地址 `<Tillbox 对外地址>/web-api/channels/<渠道编号>/notify` 和回跳地址（Tillbox 收银台）随单发送，不需要在上游后台另外配置。对外地址取 `TILLBOX_PUBLIC_URL`，没配时按请求推断，所以上游必须能从公网访问到这个地址。收到回调先验签（V1 MD5，V2 RSA 并检查时间戳不超过 300 秒），再核对商户号、订单号和金额，都对上才到账；回调处理成功回 `success`。另外每 15 秒查一次待支付订单，过期后 10 分钟内每分钟查一次；付款人点“我已付款”会立即查一次。

上游给二维码时收银台直接展示；只给跳转链接或要提交表单时，收银台给“去付款”按钮。调用方下单没带 `type`、渠道又开放了多种方式时，付款人先在收银台选择；只开放一种时直接用它。预下单失败时调用方会收到“支付通道暂时不可用”，订单仍待支付，用同一订单号重试会重新预下单。金额超出上游的单笔限额时，调用方收到的是具体原因，例如“支付宝单笔最低 0.30 元”（`code=-1`）；Tillbox 记下这个限额后，同样金额的订单直接拒绝、不再建单，规则见 [channels.md](channels.md) 第 3.3 节。

订单过期后上游才确认的付款仍自动到账并通知商户，同时记一条待处理的迟付异常，提醒到商户后台核对是否入账（原因见[订单过期后才到的成功通知](#订单过期后才到的成功通知)）。金额和订单原价不符、订单已支付后又确认另一笔、订单已关闭后才确认的，都不自动到账，只记异常。接口退款同样不支持，需要到上游处理。

## 4. 上线验收顺序

以下步骤需要实际账户操作，尚未由本地模拟测试替代：

1. 在支付宝后台核实应用账务明细权限、应用公钥、支付宝公钥和经营码所属账户。在 Tillbox“支付渠道”里打开该经营码渠道测试连接，确认使用正式环境并启用；商户选用这个渠道。
2. 在一个调用方创建一笔小额充值，打开 Tillbox 收银台，核对应付金额、收款名称和经营码；在支付宝真实支付一次，不重复扫描付款。
3. 在 Tillbox“订单”中确认该单已支付、实收金额正确、支付宝流水号可追溯；在“通知记录”确认送达；在调用方确认充值只到账一次。
4. 在每个接入的调用方分别完成上述流程。记录调用方版本、订单号、付款时间、确认延迟和通知结果，保留验收记录。
5. 再检查过期未付订单、故意少付的小额测试、重复通知的幂等表现，以及通知目标短时不可达后的重试。错付和迟付应进入异常，由人工核对处理。

正式收款延迟和限流阈值尚待实际观察，不建议验收前缩短默认查账间隔。涉及真实退款时通过支付宝或线下处理，再在 Tillbox 填写处理理由；API 退款明确返回不支持。

## 5. 调用方已知差异

Tillbox 接受查单时放在表单里的 `act=order`，通知里的 `money` 也原样回传下单时收到的字符串，照顾按字符串比较金额的调用方。这两处是已实现的兼容行为。这类调用方对接官方易支付时会因 `10.00` 被发成 `10` 而拒绝通知，这是官方实现的问题，Tillbox 这边已经避开；其他细节见 [兼容取舍](research/epay-compat.md)。

### 订单过期后才到的成功通知

Tillbox 订单默认 5 分钟到期（可设 1–30 分钟）。付款发生在到期前、查账稍晚的，仍按正常到账通知；到期后 24 小时内的迟付经申诉核实补认后，也会发出成功通知。调用方对这种通知的处理不同：有的只要自己的订单还没入账就照常入账；有的在订单失效一段时间后仍回 `success`，但不入账。

后一种情况 Tillbox 会把通知记为送达，无法自行发现对方没入账。所以补认迟付时，如果调用方那边的订单可能已经失效，管理员要到调用方后台核对该订单；显示已过期的，手动给用户补充值。调用方在自己的订单失效前向 Tillbox 查一次单，可以减少这种情况。AI 补认过期订单后，处理记录会在通知送达后转人工并附带这条提醒；管理员在流水页人工补认的，需自行核对。

## 6. 已有的验证

- 官方 V1、V2 PHP SDK 对着本系统走完下单、跳转、查单、退款、通知和回跳验签；做法见 [development.md](development.md)。
- 错付、迟付、重复付款、通知退避和死信、重启后补扫由隔离集成测试覆盖。真实支付宝账户上的错付资金处理需要按第 4 节自己验收。

后台“支付测试”可以独立验证 Tillbox 收款和回调，不会给业务站充值；使用见 [operations.md](operations.md)。
