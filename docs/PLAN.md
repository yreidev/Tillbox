# Tillbox 计划

兼容易支付协议的自托管收款系统：用支付宝经营码收款，定时查账务明细，靠金额尾数确认到账。

- 收款原理：[research/collection-principle.md](research/collection-principle.md)
- 易支付协议规格（V1 + V2，按官方实现对齐）：[research/epay-protocol.md](research/epay-protocol.md)
- 易支付兼容取舍（常见调用方的用法、和官方不同的地方）：[research/epay-compat.md](research/epay-compat.md)

## 已定

| 项 | 结论 |
| --- | --- |
| 名称 | Tillbox（原名 TailPay，因为和别人的支付品牌重名，2026-10-15 改名） |
| 许可证 | AGPL-3.0 |
| 后端 | Go，模块路径 `tillbox` |
| 前端 | HeroUI v3（React，开源版）+ Tailwind CSS v4，图标 Gravity UI Icons（2026-10-17 由 Semi Design 换成） |
| 一期范围 | 只实现支付宝经营码一个渠道；但先把渠道层设计成可插拔接口，为以后接微信、当面付留位置。易支付协议层只依赖渠道接口，不依赖具体渠道 |
| 数据库 | SQLite 和 PostgreSQL 都支持，默认 SQLite，配置切换。服务按单实例设计（查账任务和金额分配都要求串行），PostgreSQL 下也不做多实例 |
| 数据访问 | Bun（按方言生成 SQL）+ goose（迁移为 SQL 文件，SQLite 和 PostgreSQL 各一套目录） |
| 后台前端 | Vite + React 19 + TypeScript + `@heroui/react`；路由 TanStack Router，数据请求 TanStack Query；表格和表单用 HeroUI 组件，公共封装在 `web/src/lib/`（见 ui.md） |
| 前端二维码 | `uqr` 绘制，`zxing-wasm` 识别上传的经营码图片；WASM 随构建提供 |
| 支付宝 V3 签名 | 自行实现请求签名和响应验签，保留原始响应体；评估的 Go SDK 公钥模式不能满足响应验签要求 |
| 部署 | 前端打进 Go 单二进制；只发布 amd64 Docker 镜像。启动参数（监听地址、数据库连接串、公网地址、可信代理）走环境变量；支付宝密钥、商户、查账间隔等业务设置存库、在后台改，敏感字段用主密钥加密 |
| 易支付协议 | V1（MD5：`/submit.php`、`/mapi.php`、`/api.php?act=…`）和 V2（RSA：`/api/pay/*`、`/api/merchant/*`）都实现，按官方服务端和官方 SDK 的实际行为对齐；和官方不同的地方逐条写在 epay-compat.md |
| 商户模型 | 多商户（多个 pid），每个商户有：MD5 密钥、RSA 公钥（可选）、密钥类型（MD5 和 RSA 都收 / 只收 RSA）、通知和回跳域名白名单；可单独停用、单独统计。所有商户共用一个收款账户和同一个金额池。平台有一对 RSA 密钥，在后台生成，私钥用主密钥加密存库，公钥交给商户 |
| 渠道抽象 | 按确认方式分两条路。公共接口只管"给付款人什么收款指引"；推断型渠道只负责拉流水，金额池和对账放在核心里公用；确认型渠道负责预下单、回调和查单。一期只实现推断型（支付宝经营码），确认型只定义接口 |
| 收银台 | 和后台同一套前端，是其中一个公开页面。`/submit.php` 验签建单后 303 跳到收银台路由。为了手机打开快，用 TanStack Router 按路由拆包，收银台只加载自己用到的代码，不下载后台页面 |
| 后台功能（一期） | 必做：登录（个人自用，只有一个管理员，只输密码，没有用户名；首次启动随机生成密码打印在日志里，忘了用 `tillbox reset-password` 重置）、商户管理、收款设置（支付宝密钥、经营码、查账间隔）。另外做：订单（列表、筛选、详情、手动关闭、导出 CSV）；流水与异常处理（流水列表、待处理异常、手动关联和撤销关联）；通知记录（投递记录、手动重发）；概览统计（今日金额和笔数、待处理数、近 7/30 天趋势，按商户拆分） |

## 里程碑

2026-10-15 确认：M1–M6 按下表全部做完。

每个里程碑结束都要能跑通对应测试；支付宝接口全程用本地假服务器（同样的签名和验签）做测试，不依赖真实账户。

官方易支付 SDK 没有许可证，不放进仓库。对齐测试的脚本由运行的人指定 SDK 所在目录，生成的签名样例是纯数据，可以入库。互通测试需要 Docker（PHP 容器），设成可选，不放进默认的 `go test`。

| 编号 | 内容 | 完成标准 |
| --- | --- | --- |
| M1 工程骨架 | Go 模块、环境变量配置、SQLite/PostgreSQL 连接与两套 goose 迁移、Bun、HTTP 服务；前端 Vite + TanStack 骨架、按路由拆包、打进二进制；Dockerfile | 两种数据库都能启动并完成迁移；单二进制能打开空白后台和收银台路由 |
| M2 易支付协议层 | 商户（MD5 密钥、RSA 公钥、密钥类型）和平台 RSA 密钥对；V1 / V2 签名与验签、V2 时间戳；V1 `/submit.php`、`/mapi.php`、`/api.php`（order、query、orders、settle、refund）；V2 `/api/pay/*`（submit、create、query、refund、refundquery、close）和 `/api/merchant/*`（info、orders），`/api/xxx` 和 `/api.php?s=xxx` 两种路径都认；订单记下版本，以后按版本决定通知怎么签名；订单状态、`pid + out_trade_no` 幂等、金额尾数池；渠道接口定义；先用假渠道跑通 | ① 签名向量：用官方 V1、V2 SDK 生成签名样例（含中文、空值、全空白值、额外参数），存成测试数据，本系统算出的签名和验签结果要完全一致。② 互通测试：在 PHP 容器里用官方 SDK 对着本系统（假渠道）走完 V1 和 V2：表单下单、链接下单、接口下单、查单、退款（应当返回不支持）、关单，响应都能通过 SDK 验签。③ 按常见调用方的请求形态（额外参数、空的 `sign`、表单里的 `act`）构造的请求，能下单和查单。④ 金额池在并发下不会重复分配 |
| M3 支付宝查账 | V3 请求签名与响应验签、账务明细分页拉取、超量切窗、活跃/常规/收尾节奏、三档补扫、失败退避、流水入库去重和冲突记录 | 对假服务器的各种返回（分页、迟到流水、验签失败、限流）行为正确；重启后节奏能恢复 |
| M4 对账、通知、收银台 | 匹配规则和异常分类、人工关联和撤销；通知队列：GET 请求，V1 订单用 MD5 签名，V2 订单用 RSA 签名，每次发送都重新签名并带上当时的时间戳；正文包含 success 就算送达；重试时间点见 epay-compat.md；之后进死信，可手动重发；跳回 `return_url` 时带签名参数；收银台页面（金额、二维码、倒计时、"我已付款"） | 端到端：下单 → 假流水到账 → 自动确认 → 通知送达，并且通知能通过官方 V1 SDK（`verifyNotify`）和 V2 SDK（`verify`）验签；各类异常能正确分类 |
| M5 后台 | 登录、商户管理（MD5 密钥、RSA 公钥、密钥类型、域名白名单）、平台 RSA 密钥（生成、查看公钥）、收款设置（生成应用密钥、经营码识别、查账间隔）、订单、流水与异常处理、通知记录、概览统计 | 所有后台操作都能在浏览器里完成，不用改库 |
| M6 联调与发布 | 调用方实际接入；真实支付宝小额收款验证；部署文档；发布镜像 | 调用方能完成一次真实充值；文档写到 `docs/` |
